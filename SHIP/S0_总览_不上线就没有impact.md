# S0 · 送上线总览 —— 不上线,就没有 impact

> **目标**:想清楚你的项目该走哪条上线路径,建立"静态 vs 动态"的判断力。
> **前置输入**:BUILD 支柱做完(本地能跑通的前端 + 后端)。
> **产出物**:—(读);为 S1–S4 选好路线。
> **配套 skill**:—

## 先打个气:上线没有你想的那么可怕

你已经把最难的部分做完了——一个能跑的 agent。剩下的"上线",本质上就是**把电脑里的东西,搬到一台一直开着的公网服务器上**,再拿到一个网址。

i2i:**Idea → Build → Ship → Impact**。你走到了 Ship。一个躺在你笔记本里的 agent,影响力是**零**;把网址发出去,哪怕只有一个真实用户用上了,就有了 impact。这一步,是"作业"变成"作品"的那一下。

## 新想法:先分清「静态」还是「动态」

上线前先问一句:**你要上线的东西,需不需要"实时调模型"?**

| | 静态(Static) | 动态(Dynamic) |
|---|---|---|
| 是什么 | 只有界面 / 展示内容,不真的对话 | 要真调模型、真对话、真存数据 |
| 例子 | 项目介绍页、作品集、设计说明 | 你的聊天 agent 本体 |
| 放哪 | **GitHub Pages**(免费最简单) | 前端放 Pages,**后端放 Railway**(默认) |
| key | 没有 key | key **只在后端** env,前端永远看不到 |

**大多数小组是"混合":前端(静态页)放 GitHub Pages,后端(FastAPI)放 Railway,前端调后端。** 这正是运行示例 `example_project/端到端示例_考前3分钟/` 的结构,也是 HEAI(renben.ai)的简化版。

## 三个平台,各就各位

- **GitHub Pages**(S1):放**静态前端**。免费、你已经在用 GitHub。
- **Railway**(S2):放 **Python 后端(FastAPI)**。自动识别 Python、持久进程、三个真实项目同款。**成本:非永久免费(~$5 试用/hobby)。**
- **Vercel**(S2 备选):**免费**替代。原生跑 Node serverless 顺;跑 Python 稍麻烦。零成本演示可用。
- **腾讯云/阿里云**(S4 备注):要长期给**国内用户**用、且访问要稳,再考虑(需实名 + 少量费用)。

## 痛点对比

| 😌 简单·看不出必要 | 「我本地能跑就行,截图给老师看不就好了」——demo 一关,别人永远用不上,也没人能在手机上试 |
| 🔥 复杂·痛点凸显 | 答辩时评委说"发我个链接我试试"——没上线的项目当场哑火;而真实用户(一个考前焦虑的学生)不会打开你的终端敲命令,只会点一个网址 |

## 门禁检查(过了才进 S1)

- [ ] 分清了你的项目哪些是静态、哪些要动态
- [ ] 选好了路线(纯静态展示 / 前端 Pages + 后端 Railway)
- [ ] 知道 key 只能待在后端,不进前端、不进 git
- [ ] 接受成本安排(Railway ~$5,或改用 Vercel 免费路径)

## 思考题

> 如果你的后端某天挂了(欠费、网络、模型额度用完),用户会看到什么?
> 是一个吓人的报错白屏,还是一句温和的兜底 + 危机热线?这个问题,S3 会让你必须回答。
