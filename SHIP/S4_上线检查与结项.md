# S4 · 上线检查与结项 —— 把责任兜住,交出成品

> **目标**:上线前逐条过一遍检查清单(尤其密钥安全与危机护栏),并产出一份结项技术文档。
> **前置输入**:整体上线的应用(S3)。
> **产出物**:上线检查清单全过 + `结项技术文档`(对齐 `2_hcai_guide` T8 第 4 节技术架构)。
> **配套 skill**:`/ship-golive`

## 先打个气:上线的最后一公里,是"负责任"

技术上你已经成功了。这一步不加功能,只做一件事:**在把网址发给真实用户之前,确认它不会伤到人、不会泄露 key**。这正是你心理/教育专业最该把关的地方。

## 新想法:上线检查清单(逐条勾,别跳)

用 `templates/上线检查清单.md`,五组逐条过:

1. **密钥安全**(一票否决):
   - `grep -rniE "sk-[a-z0-9]{16}" 前端目录` = **零**
   - key 只在平台 Variables;`.env` 在 `.gitignore`;`git log -p | grep sk-` 无结果
2. **可用性**:公网 URL 能打开 + 完整对话一轮 + **手机测过**
3. **内容合规**:界面明示"我是 AI,不能替代专业帮助" + 隐私一句话(不采集真实身份)+ **危机热线正确**(全国 **12356**;北京 **010-82951332**;紧急 **120**)
4. **优雅降级**:后端 / 模型失败时给兜底,不白屏、不甩报错栈
5. **README 三要素**:是什么(一句话:帮谁在什么场景解决什么)+ 怎么用(网址 + 示例输入)+ 谁做的(小组 + 课程)

## 新想法:结项技术文档(技术架构那一章)

结项要交的"完整项目文档",技术架构章(对齐 2_hcai T8 第 4 节)写清:
- **架构图**:用户 → 前端(Pages)→ 后端(Railway)→ 模型(OpenRouter);标出 key 在哪
- **技术选型**:前端(静态 HTML)/ 后端(FastAPI 包 mini CC harness)/ 部署(Pages + Railway)+ 为什么这么选
- **安全设计**:key 走后端、危机确定性拦截、子 agent 复核、优雅降级
- **复现步骤**:别人怎么把它跑起来(装依赖、填 env、起服务)
- **已知限制**:还没做的、不适用的场景

## 国内访问备注

GitHub Pages / Railway 在国内访问**可能不稳**。若要长期给国内用户用:
- 前端可迁到**腾讯云 / 阿里云静态托管**;后端可迁到**云函数 / 轻量服务器**。
- 代价:需**实名认证 + 少量费用**(还可能要 ICP 备案)。
- 策略:**课堂答辩 → Pages + Railway 够用;真要长期服务国内用户 → 再迁国内云。**

## 痛点对比

| 😌 简单·看不出必要 | 「能跑就交了,检查清单太麻烦」——结果前端漏了个 key、或危机时它开始"劝解",这些在 demo 里看不出,却是真实伤害 |
| 🔥 复杂·痛点凸显 | 把网址发出去 = 对真实用户负责。清单化上线,是把"应该没问题"变成"逐条确认过"——这是专业和业余的分水岭 |
