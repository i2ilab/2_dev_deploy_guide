## P04 · 一次请求的旅程(6 步)

**【页面要点】** 6 步时间线:输网址 → 查地址(DNS) → 发请求 → 服务器处理 → 传回来(HTTP 响应) → 浏览器渲染。

**【讲解】** 用"打电话点外卖"类比:你报地址(输网址)→ 查号台找到餐馆电话(DNS 把域名翻成 IP)→ 打过去点单(发请求)→ 餐馆做菜(服务器处理)→ 送回来(响应)→ 你摆盘开吃(浏览器渲染成页面)。这趟旅程每次点开网页都在发生。**为什么要懂它?** 报错时你能判断卡在哪一步:是"打不通电话"(网络/后端没起)还是"菜做错了"(后端逻辑错)。

## P05 · 客户端 vs 服务器

**【页面要点】** 左:客户端 CLIENT(前端)= 你的浏览器,跑 HTML/CSS/JS 画界面,**公开的→绝不放 key**。右:服务器 SERVER(后端)= 一直开机的远程电脑,跑 agent、藏 key、连模型,**私密的**。

**【讲解】** 这是全课最重要的一分为二。**前端 = 浏览器里的东西 = 所有人都能看**(右键就能看源代码)。**后端 = 远处服务器里的东西 = 用户看不到**。回忆 2_dev_deploy 的三层架构(前端→后端→模型),现在你知道前两层各自住在哪、谁公开谁私密了。这条线记牢,P29 的安全红线就是它的直接推论。

## P06 · HTTP · 静态 vs 动态 · 域名

**【页面要点】** 三张卡:HTTP(S)=浏览器和服务器的对话规矩,S=加密 / 静态=只发写好的文件(GitHub Pages 免费)/ 动态=服务器现场生成、调模型(要后端 Railway)。底部:域名 + DNS。

**【讲解】** **静态 vs 动态**是你部署时的第一个岔路口。静态页就像一张已经印好的海报,谁来都发同一张(展示页、作品集)——放 GitHub Pages,免费。动态就像现做的奶茶,每个人点的不一样,得有人现场做(能对话的 agent)——需要后端服务器。你的项目通常是"一静一动":静态展示页 + 动态对话后端。**域名**是人好记的地址(yourname.github.io),**DNS** 负责翻译成机器认的 IP。

## P08 · 三件套总览(盖房子比喻)

**【页面要点】** 三张卡:HTML=结构/骨架(墙和房间)/ CSS=外观/装修(刷漆铺地板)/ JavaScript=行为/电路(按开关有反应)。

## P09 · HTML 骨架

**【页面要点】** 左:index.html 真实代码片段(header/h1/form/input/button)。右:三个词——标签 tag(一对,包住内容)、元素 element(一个完整盒子)、属性 attr(placeholder/id/class)。

**【讲解】** HTML 就是"用标签把内容装进盒子"。`<button>发送</button>` 就是一个按钮盒子,`<button>` 和 `</button>` 是一对标签,中间是内容。属性像给盒子贴的标签纸(`placeholder="说说"` 是输入框里的灰字提示)。你不用记所有标签,认得几个常见的(button 按钮、input 输入框、div 通用盒子)就够看懂结构了。

**【🤖/👁】** 🤖 Claude Code 自动写好所有标签、嵌套、属性。👁 你要认得 `<button>`/`<input>` 大概是什么,能对它说"加一个危机求助按钮"。

## P10 · CSS 外观

**【页面要点】** 左:三件事——选择器(选中哪些盒子)、盒模型(内边距/边框/外边距)、布局(flex 自动排队 vs 绝对定位)。右:CSS 代码片段(.btn 背景色/圆角/内边距)。

**【讲解】** CSS 回答"这个盒子长什么样、放哪里"。**选择器**是"点名"——`.btn` 表示所有 class 叫 btn 的盒子。**盒模型**是每个盒子都有的三层(内容→内边距→边框→外边距),知道这个,你就懂为什么调"间距"有好几个地方。**布局**两种主流:flex(让盒子自动排队对齐,最常用)和绝对定位(指哪打哪,像我们做 slides 那样)。颜色用 `#C2410C` 这种十六进制码。

**【🤖/👁】** 🤖 自动写全部样式,还能一句话改配色/圆角。👁 认得 color/background/padding,能说"配色换成温暖治愈风、按钮圆角大一点"。

## P11 · JavaScript 交互(变量/函数/事件)

**【页面要点】** 左:三个基本功——变量(存东西,如 history)、函数(可反复调用的动作)、事件(onclick/onsubmit 触发函数)。右:index.html 的 form.onsubmit 片段。底部:DOM = JS 操作页面的方式。

**【讲解】** 前面两样是"静"的,JavaScript 让网页"活"起来。**变量**是贴了名字的盒子(`history` 存聊天记录)。**函数**是一段起了名的动作,随叫随到。**事件**是"什么时候动"——用户点按钮(onclick)、提交表单(onsubmit),就触发对应函数。**DOM** 是个术语,意思是"JS 用来增删改页面元素的接口"——听到别慌,就是"JS 动页面的手"。

## P12 · fetch:前端 → 后端

**【页面要点】** 左:index.html 的 fetch 代码(POST /api/chat,body 是 JSON.stringify(messages),await r.json())。右:一句话——前端把用户的话发给后端 /api/chat,后端跑 agent 回 reply,前端显示成气泡。

**【讲解】** 这是前端最关键的一招,务必讲透。**fetch = 网页向后端"打电话"**。用户在输入框打字,前端用 fetch 把这句话打包(JSON)发给后端的 `/api/chat`,后端跑你的 agent、把回复发回来,前端再显示出来。你运行示例前端的 `sendMsg()` 干的就是这件事。理解了 fetch,你就理解了"前端和后端是怎么连起来的"——这正是 B4 连通那一步的核心。

**【🤖/👁】** 🤖 写好 fetch、错误处理、降级。👁 认得 fetch=调后端;能说"后端连不上时要有兜底提示,别白屏"。

**【讲解】** 前端后端能对话,靠的是三样约定:用什么格式传数据(JSON)、后端开放哪些功能(API)、每次请求成没成(状态码)。这一节把它们讲清,你就能看懂前后端之间"说了什么"。

## P14 · JSON

**【页面要点】** 左:JSON 代码(messages 数组,role/content)。右:JSON 就是"键: 值"清单,人和机器都读得懂;前端发 JSON、后端回 JSON;你在 1_claude_code_basic 见过它。

**【讲解】** JSON 是前后端之间的"普通话"——一种双方都认的通用格式。长得像"键: 值"的清单:`{"role":"user","content":"我好紧张"}`。你不用会写,认得大括号 `{ }` 和引号里的 key(键名)就够了。你的 agent 输出协议本身就是 JSON(`{"reply":"..."}` 或 `{"tool":"..."}`),这在模块 1 你已经见过。前后端能对齐,全靠都说 JSON 这门"普通话"。

## P15 · API 与 REST

**【页面要点】** 三张卡:API=接口(后端的点单窗口)/ 端点 endpoint=一道菜的地址(/api/chat、/api/health)/ 方法 method=怎么点(GET 取数据、POST 提交)。底部:REST=大家都遵守的点单规矩。

**【讲解】** **API 就是后端对外的"菜单"**——它规定了前端能点哪些菜、怎么点。每道菜有个地址,叫**端点**(`/api/chat` 是聊天、`/api/health` 是体检)。点菜的动作叫**方法**:GET 是"取点东西看"(如查体检结果),POST 是"提交点东西"(如发一条消息)。**REST** 是一套约定俗成的点单规矩,让所有人的 API 都长得差不多、好懂。你运行示例的后端就开了这两道菜。

## P16 · 状态码

**【页面要点】** 四行:200 成功 / 400·401 你发的请求有问题(参数错/没权限) / 404 找不到(地址写错/端点不存在) / 500 后端自己崩了(去看日志)。

**【讲解】** 状态码是后端给你的"回执",是**看懂报错的第一步**。记住四类就够:**200** 一切正常;**400/401** 是"你点错单了"(参数写错、key 不对);**404** 是"这道菜不存在"(地址/端点写错);**500** 是"后厨着火了"(后端代码崩了,得去看后端日志)。学会认这四类,你报错时就能对 Claude Code 说清"是 404 还是 500",它才好对症下药。

## P17 · 分节:前端框架

**【页面要点】** PART 04。框架是给复杂界面用的"工具箱";简单的用纯静态就好。

**【讲解】** React、Next.js 这些词你肯定听过。这一节讲清:它们是什么、解决什么问题、以及最重要的——**什么时候你根本不需要它们**。

---

## P18 · 为什么要框架

**【页面要点】** 左(绿):纯静态 HTML 就够(一两个页面、展示页、简单 demo → 一个 index.html + Pages)。右(蓝):该上框架了(很多页面、要登录、要管很多状态、重复的界面块)。底部:能静态就静态。

**【讲解】** 关键判断:**能用纯静态,就别上框架**。如果你只是一个聊天页、一个展示页,一个 `index.html` 就够了,简单又好维护。什么时候才需要框架?当界面变复杂:很多页面要来回跳、要用户登录、有大量重复的界面块(比如一长串卡片)、要"记住"很多状态。框架就是为管理这种复杂度而生的工具箱——**不是越高级越好,是合适才好**。

---

## P19 · React

**【页面要点】** 三张卡:组件 component(可复用的界面积木,一个"消息气泡"写一次到处用)/ props(给组件传参数)/ state(组件的"记忆",变了自动重画)。底部:React 19(2026 最新)。

**【讲解】** React 的核心思想是"**把界面拆成积木**"。一个"消息气泡"做成一个**组件**,写一次,到处复用。给组件传不同的**props**(参数),就能显示不同的文字/颜色。组件还有**state**(状态/记忆),比如输入框里的字、聊天历史,状态一变,界面自动重画,不用你手动更新。你不用手写 React,但要认得"组件、状态"这两个词——Claude Code 生成 React 项目时,你才知道它在说什么。

---

## P20 · Next.js + 三项目选型

**【页面要点】** 左:Next.js 多给的——页面路由、前后端一体、SSR(服务器先渲染,首屏快)。右:三真实项目怎么选(小智 Next 静态导出 / Agent Leo Next14 全栈+账号 / HEAI 纯 vanilla HTML)。底部:越复杂越可能上 Next。

**【讲解】** **Next.js 是 React 的"全能版"**:除了 React 的组件,还帮你管页面路由、把前端和后端 API 装在一个项目里、并支持 SSR(服务器先把页面渲染好再发,首屏更快、更利于搜索引擎)。2026 最新是 Next.js 16(默认用了更快的 Turbopack)。看老师三个真实项目就懂选型规律了:**HEAI 够简单 → 纯 vanilla HTML;小智要打包成 App → Next 静态导出;Agent Leo 要账号系统和多 agent → Next 全栈**。复杂度决定要不要框架,不是赶时髦。

## P22 · 后端用什么写(Node vs Python）

**【页面要点】** 左:Node.js(用 JavaScript 写后端,一种语言通吃,Next/Vercel 原生)。右:Python + FastAPI(你已会 Python,FastAPI=最短路径把 Python 变 API,Railway 自动识别,=HEAI 同款)。底部:本课默认 Python+FastAPI。

**【讲解】** 后端可以用不同语言写。**Node.js** 是"用 JavaScript 写后端"——好处是前端也是 JS,一种语言从头用到尾。**Python + FastAPI** 是本课的默认——因为你在 `0_agent_basic` 已经会 Python,心智不用切换,而 FastAPI 是把 Python 变成一个 Web API 的最短路径,Railway 还能自动识别它。两条路都对,选你顺手的;本课选 Python 是为了不给你增加负担。

## P23 · FastAPI 拆解

**【页面要点】** 左:main.py 骨架(app=FastAPI(); @app.get("/api/health") 返回 {"status":"ok"}; @app.post("/api/chat") 跑 run_harness 返回 {"reply":...})。右:认得三样——@app.get/post 开一道菜、里面=收到请求做什么、return {…} 回 JSON。底部:key 从 os.environ 读。

**【讲解】** 别怕后端代码——你运行示例的后端其实就几行。`@app.get("/api/health")` 就是"开一道叫 /api/health 的菜";下面的函数是"收到请求时做什么";`return {...}` 是"回一段 JSON"。`@app.post("/api/chat")` 收到用户消息,跑你的 harness,把回复返回。**后端三大职责**:藏 key(从 `os.environ` 读,绝不写死)、跑你的 agent 逻辑、连模型。看懂了这张骨架,B2 后端服务化那一步你就有底了。

## P24 · 数据与存储

**【页面要点】** 三张卡:先用文件/内存(够简单就别上数据库,端到端示例日记存文件即可)/ 何时要数据库(要长期记住很多用户/历史:账号、跨设备)/ Supabase 一瞥(最省事的托管数据库,Agent Leo 用它)。底部:别过早上数据库。

**【讲解】** "要不要数据库?"——多数课堂项目答案是"先不要"。如果只是演示、数据不多,存在文件或内存里就够了(端到端示例把情绪日记存成文件)。**什么时候才需要数据库?** 当你要长期记住很多用户、要账号登录、要跨设备同步、数据量大。那时再上 **Supabase** 这类托管数据库(开箱即用,Agent Leo 就用它存账号和对话)。原则:**先跑起来,别过早上数据库**——复杂度是逼出来的,不是一开始堆上去的。

## P27 · 浏览器 DevTools

**【页面要点】** 三张卡:查看源代码(右键→看源码,验证前端有没有泄漏 key)/ Console 控制台(看 JS 报错,红字先截图)/ Network 网络(看每个请求成没成,/api/chat 是 200 还是 404/500)。底部(红):前端是公开的,右键就能看到一切。

**【讲解】** 按 **F12** 打开开发者工具,这是你排错的"透视镜"。**查看源代码**能看到前端的一切——这也证明了"前端是公开的",所以 key 绝不能放前端。**Console**(控制台)是 JS 报错出现的地方,看到红字先截图发给 Claude Code。**Network**(网络)能看到每个请求成没成——你的 `/api/chat` 到底是 200(成)还是 404/500(败),一眼看到。学会用这三样,你排错时就不再抓瞎。

## P28 · 看懂常见报错

**【页面要点】** 四行:白屏/转圈(前端崩或后端没连上→看 Console+Network)/ CORS 报错(后端没允许前端域名→CORS_ORIGINS 加前端网址)/ 404(地址写错→检查 fetch 的 URL)/ 500(后端崩→看 Railway 日志)。

**【讲解】** 这四个是零基础同学最常撞的坑,提前认识,遇到就不慌。**白屏/一直转圈**:多半是前端 JS 崩了或后端没连上——看 Console 红字 + Network 有没有失败请求。**CORS 报错**:后端没允许你的前端域名跨域访问——在后端 `CORS_ORIGINS` 里加上前端网址就好(这正是 B4 讲的)。**404**:地址写错了——检查前端 fetch 的 URL 对不对。**500**:后端代码崩了——去 Railway 看后端日志找异常。**看懂报错 = 会指挥的一半**:你能说清"哪一层、什么错",AI 就修得又快又准。

## P29 · 结课清单「看懂 + 会指挥」

**【页面要点】** 两栏勾选清单(绿):说得清前端/后端/模型各是什么住哪、看懂 HTML/CSS/JS 三段、知道 fetch=前端调后端、认得 JSON/API/状态码、知道何时纯静态何时上框架、报错时看 Console/Network 说清哪层。底部(红):唯一铁律——前端是公开的,key 只能待在后端。

**【讲解】** 对照这张清单自检:如果这些你都能点头,恭喜——你已经具备"看懂 + 会指挥"的地基了。你不会手写这些代码,但你能读懂 AI 写的、能把需求说到点子上、能在报错时接住。最后再强调那条贯穿全课的**唯一铁律**:前端是公开的,任何人右键就能看源码,所以 **key 只能待在后端**。这一条,比其它所有都重要。
